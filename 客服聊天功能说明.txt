========================================================
客服实时聊天 + RabbitMQ 排队功能 说明文档
========================================================

一、新聊天功能与旧版本有什么区别？
--------------------------------------------------------
区别很大——之前的版本实际上完全不能用，是个空壳。

【之前的版本（有骨架但全是坏的/假的）】

1. 前端客服页面（ServiceMain.vue）
   纯假数据：用户列表写死小明/小红/阿伟/静静，聊天记录是
   硬编码的，点谁就显示两句写死的话。

2. 前端客户端
   根本没有聊天页面，用户无处联系客服。

3. 前端 WebSocket
   一行都没有，没装 socket 库也没封装，压根连不上后端。

4. 后端依赖注入
   @Autowired 直接标在 @ServerEndpoint 的实例字段上 →
   全部注入为 null（WebSocket 每连接 new 一个实例，不归
   Spring 管），一用就空指针。

5. 后端鉴权
   @OnOpen(@PathParam("message")) 但 URL 是 /ws/chat
   没有这个参数 → 连接直接报错。

6. RabbitMQ
   发消息到队列了，但匹配逻辑靠 @RabbitListener 消费者调
   autoMatch()，而 autoMatch 只匹配内存队列、MQ 消息和内存
   队列不同步，匹配永远不触发或错乱。

7. 消息持久化
   没有，刷新即丢失。

8. 排队体验
   无排队位置、无等待人数、无自动重连、无断线恢复。

【现在的版本（真实可用）】

1. 用户入口
   客户端右上角下拉 → 联系客服 → 真实聊天页。

2. 通信链路
   前端 ws.js 原生 WebSocket 连接 → Vite /ws 代理 →
   后端 /ws/chat/{token}，双向实时收发。

3. 后端注入
   改静态字段 + setter 注入，修复 null 问题。

4. 鉴权
   token 放 URL 路径，连接时校验 JWT + 查角色区分客服/用户。

5. 排队
   用户申请 → 进 RabbitMQ 持久化 FIFO 队列 → 客服空闲时按
   顺序拉取匹配；用户实时看到「您前面还有 N 人」，客服实时
   看到「排队等待 N 人」。

6. 消息落库
   每条消息存 t_chat_message，接入会话时自动加载历史记录，
   刷新不丢。

7. 会话管理
   客服结束会话自动接入下一位；用户离开客服回到空闲；断线
   3 秒自动重连，排队/会话状态自动恢复。

简单说：旧版是"看起来有聊天界面的演示页面"，新版才是
"用户和客服真的能对上话"的功能。

测试步骤：启动 RabbitMQ → 执行建表 SQL → 重启前后端 →
客服先登录打开工作台 → 用户再点联系客服。


二、消息持久化是什么意思？
--------------------------------------------------------
持久化 = 把数据写到磁盘（数据库/文件）保存下来，而不是只
放在内存里。

【不持久化（旧版聊天）】

聊天消息只存在两个地方：
  - 浏览器内存（页面上的数组）
  - 后端服务内存（WebSocket 的 Map 里）

  用户发"我的支付失败了" → 只显示在屏幕上
  → 刷新页面/重启服务 → 消息永远消失

关掉浏览器、重启后端、刷新页面，聊天记录全部没了，像没
发生过一样。

【持久化（现在的版本）】

每条消息实时通过 WebSocket 转发的同时，写一条记录到 MySQL
的 t_chat_message 表：

  用户发消息
    ├── WebSocket 即时推送给客服（屏幕上立刻显示）
    └── INSERT INTO t_chat_message (发送人, 接收人, 内容,
        时间)  ← 落盘

效果：

| 场景               | 效果                                   |
| 用户刷新聊天页     | 调 GET /chat/history 从数据库拉回历史  |
| 用户断线重连       | 会话状态恢复，历史记录还在             |
| 后端服务重启       | 消息在 MySQL 里，一条不丢              |
| 客服换电脑登录     | 照样能看到和用户的完整聊天记录         |
| 出纠纷要查证据     | 数据库里有时间、双方、内容，可追溯     |

【RabbitMQ 队列也是持久化的】

用户排队消息进 user_wait_queue 时，队列声明为 durable，
消息也落盘——即使 RabbitMQ 服务重启，排队中的用户也不会
丢失，重启后客服照样能拉到。这也是一种"消息持久化"，不过
持久化的是"排队任务"，不是聊天内容。

简单记忆：内存 = 一断电就没；数据库/磁盘 = 关机重启都还在。
聊天记录属于重要业务数据，必须持久化。


三、消费者不是没了吗？
--------------------------------------------------------
消费者没消失，只是换了消费方式。RabbitMQ 有两种消息消费
模式：

【推模式（旧版，@RabbitListener）—— 已删除】

  用户入队 → 队列 → MQ 立刻"推"给
  UserQueueConsumer.listenWaitUser() → 调 autoMatch()

问题：消息一进队列立刻被消费掉。如果此时没有空闲客服，
autoMatch 匹配不上，消息已经没了——用户明明在排队，但
排队信息丢了，永远等不到客服。

【拉模式（新版，receiveAndConvert）—— 现在用的】

消费者就是 ChatWebSocket.java 里的 tryMatch() 方法：

  // 客服空闲时，主动从队列"拉"一条排队消息
  Object obj = rabbitTemplate.receiveAndConvert(
      RabbitConfig.USER_QUEUE, 500);

触发时机：客服上线、客服结束会话、用户刚入队——
只在可能存在空闲客服时才拉。

【为什么排队场景必须用拉模式】

用户 A、B、C 同时点"联系客服"，但所有客服都在忙：

  推模式：3 条消息立刻被消费者拿走
        → 没空闲客服 → 匹配失败 → 消息已消费，丢了

  拉模式：3 条消息安静躺在 RabbitMQ 队列里（durable 持久化）
        ↓
        客服1结束会话 → 主动 receive 拉一条 → 用户A → 匹配
        客服2上线     → 主动 receive 拉一条 → 用户B → 匹配
        用户C继续在队列里等（实时看到"前面还有1人"）

队列本身就是"等待大厅"：消息留在队列里 = 用户在排队；
客服主动取走 = 叫号接待。这跟银行叫号一个道理——号在取号
机（队列）里存着，柜台（客服）空了才叫下一个号，而不是号
一取出来就不管柜台忙不忙直接塞过去。

所以 @RabbitListener 那个类必须删：它一监听，消息会被它
提前抢走，客服反而拉不到了。现在的消费者角色由客服的
tryMatch() 承担，而且消费时机和"客服是否空闲"严格绑定，
这才是正确的排队语义。


四、客服端怎么实现实时通信？
--------------------------------------------------------
客服端的实时通信和用户端走的是同一条 WebSocket 长连接，
区别只在于连接后服务端根据角色分配的"身份"不同。

【连接建立】

客服打开客服工作台（ServiceMain.vue）→ onMounted 调
connectChat(token)：
  - ws.js 建立 ws://host/ws/chat/{token} 长连接
  - 后端 ChatWebSocket.onOpen 校验 JWT、查角色
  - 角色是"客服"或"管理员" → isService=true：
      · 加入 onlineServices 在线客服集合
      · 若不在会话中，加入 freeServiceQueue 空闲队列
      · 立即触发 tryMatch() 尝试接入排队用户
  - 浏览器不关，连接一直保持（HTTP 升级为 WebSocket 后是
    双向长连接，不需要轮询）

【实时消息收发】

  客服收到用户消息（服务端推送）：
    用户发 chat → 后端 handleChat() 根据绑定关系找到客服
    → session.getBasicRemote().sendText(...) 主动推给客服
    → 前端 ws.js onmessage 收到 → 分发给 ServiceMain 的
      handlers.chat → 渲染到聊天窗口

  客服发送消息：
    输入框回车 → sendChat('chat', {content}) → 后端转发给
    绑定的用户 → 同时落库 t_chat_message

【实时状态通知（服务端主动推）】

  queue_count    排队人数变化时广播给所有在线客服
                 （工作台顶部"排队等待：N 人"实时刷新）
  match_success  匹配成功，告知客服接入的用户 id/昵称
  user_leave     用户离开/结束会话，客服自动回到空闲
  chat           用户发来的聊天消息

【自动重连】

网络抖动导致连接断开 → ws.js 3 秒后自动重连 → 后端 onOpen
识别出该客服的会话绑定还在（serviceBindUser），重发
match_success 恢复聊天界面，前端再拉一次历史消息，用户
无感知。

========================================================
涉及的主要文件
========================================================
后端：
  - websocket/ChatWebSocket.java      WebSocket 端点（排队/匹配/转发/落库）
  - config/RabbitConfig.java          队列/交换机声明（durable 持久化）
  - entity/ChatMessage.java           聊天消息实体
  - mapper/ChatMessageMapper.java/.xml 消息落库 + 历史查询
  - controller/ChatController.java    GET /chat/history 历史记录接口

前端：
  - utils/ws.js                       WebSocket 封装（分发/自动重连）
  - api/chat.js                       历史消息 API
  - components/client/ClientChat.vue  用户端聊天页
  - components/service/ServiceMain.vue 客服工作台
  - vite.config.js                    /ws 的 WebSocket 代理配置

数据库：
  CREATE TABLE t_chat_message (
    message_id INT PRIMARY KEY AUTO_INCREMENT,
    from_user_id INT NOT NULL,
    to_user_id INT NOT NULL,
    content VARCHAR(1000) NOT NULL,
    send_datetime DATETIME NOT NULL
  );
